17. HOSTING RECOMMENDATION
------------------------------------------------------------

Requirements recap: always-on process, WebSocket support (outbound to
CoinDCX, not inbound), background scheduler, Python/FastAPI, environment
secrets, HTTPS, automatic restart, reasonable cost, suitable for a
student project.

| Option | Always-on | WebSocket-friendly | Managed Postgres | Cost for this workload | Verdict |
|---|---|---|---|---|---|
| **Railway** | Yes | Yes (no idle-sleep on paid usage-based plan) | Yes, one-click, same project | Usage-based; a single small always-on FastAPI service + a small Postgres instance is typically a few dollars/month, often coverable by trial credit for a while | **Recommended** -- simplest path from this exact repo (Dockerfile or Nixpacks both work), Postgres and the API live in the same project, secrets UI, auto HTTPS on a generated domain |
| **Render** | Only on a PAID web service | Yes, but the FREE tier spins down after ~15 min idle -- this would silently kill the persistent CoinDCX WebSocket and lose scheduler state between requests | Yes, managed Postgres add-on | Free tier unsuitable for this app specifically; paid tier (~$7/mo+) works fine | Good alternative only on a paid plan -- explicitly avoid the free tier for this app |
| **Fly.io** | Yes (small persistent VM/"machine") | Yes | Yes (Fly Postgres or an external managed Postgres) | Low, but requires more manual configuration (`fly.toml`, volumes) than Railway for an equivalent result | Solid alternative if comfortable with a bit more DevOps setup |
| **A plain VPS** (DigitalOcean/Hetzner) | Yes | Yes | Self-managed (more ops burden) | Cheapest raw compute, but you own patching/monitoring/TLS (though Caddy/Nginx + Let's Encrypt make TLS easy) | Most control, most manual maintenance -- reasonable if already comfortable with basic Linux server administration |
| Vercel serverless functions (for the backend too) | No | No -- functions don't hold a persistent outbound connection | N/A | N/A | **Explicitly ruled out** -- would kill the scheduler and WebSocket the moment a function instance recycles, exactly the failure mode `docs/deployment.md` has warned about since Phase 4 |

**Recommendation: Railway** for the backend, Vercel for the frontend
(as already planned). Reason: the lowest setup friction for exactly this
repo's shape (one Dockerfile, one FastAPI process, one Postgres database,
all always-on), a real managed Postgres in the same place, and no
idle-sleep trap that would silently break the live WebSocket/scheduler --
the single failure mode most likely to bite a first-time deploy of this
specific app. Fly.io is a reasonable second choice for a slightly cheaper
long-term steady-state cost if the extra manual configuration is
acceptable.

============================================================
4. TARGET DEFINITION
============================================================

Triple-barrier labeling (ml/labeling.py: compute_triple_barrier_labels),
NOT "will price go up." At each bar T:

  1. A hypothetical LONG and a hypothetical SHORT are both entered at bar
     T+1's open (matches the Backtester's own next-bar execution).
  2. Each gets a stop/target sized off ATR(T) (known at T, not future):
     take-profit = 2.0x ATR, stop-loss = 1.0x ATR (2:1 reward:risk).
  3. Both are simulated forward up to 12 bars (~48h on 4h) to see which
     barrier is hit first.
  4. Label = LONG if the long hypothetical hits target before stop; SHORT
     for the mirrored case; NO_TRADE if neither resolves favorably, if
     both do (an ambiguous whipsaw), or if the configured minimum 1.5:1
     risk:reward isn't met.

Feature timestamp: bar T (causal only). Label timestamp: resolved using
bars T+1..T+12 (the label is ALLOWED to look forward -- that is what makes
it a label; the barrier WIDTH is read from ATR(T) only, never future ATR).
Leakage prevention: tests/leakage/test_label_leakage.py,
tests/unit/test_labeling.py.

Label distribution on the full dataset: LONG 28.12%, SHORT 26.90%,
NO_TRADE 44.98% -- a real, non-degenerate 3-class problem, not a
near-constant label that would make any model look artificially accurate.

Training window: chronological embargoed split, embargo = 12 + 2 = 14 bars
at every split boundary (large enough that no training/validation label's
forward-looking window can leak into the next split -- see
ml/evaluation/ml_pipeline.py: chronological_split_with_embargo). Single
split: 60% train / 20% validation / 20% test (OOS), matching Phase 3's own
methodology (docs/ml_methodology.md), re-run here on the current, larger
dataset rather than assumed unchanged.
Rolling walk-forward (Stage 2, survivors only): train_window=1500,
val_window=300, test_window=300, step=300, embargo=14 -- 15 non-
overlapping OOS folds per candidate.

5-6. MODELS TESTED + HYPERPARAMETERS
============================================================

Logistic Regression, Random Forest, XGBoost, LightGBM -- all four already
implemented in ml/training/trainer.py, reused unchanged. "Ensemble"
(soft-voting over RF/XGB/LGBM) was NOT run -- a documented, pre-existing
bug (sklearn's VotingClassifier re-fits internal clones without an eval
set, which breaks LightGBM's early-stopping callback; see
docs/known_limitations.md) that this pass did not attempt to fix, since
four working model families already satisfy the task's "at minimum"
requirement and none of the simpler models showed enough promise to
justify escalating further (no LSTM/Transformer was investigated, per the
explicit instruction to only do so if simpler models fail).

Fixed, pre-declared hyperparameters (never tuned per fold or on test data):
  XGBoost:   n_estimators=500, max_depth=6, learning_rate=0.01,
             subsample=0.8, colsample_bytree=0.8, min_child_weight=5,
             gamma=0.1, reg_alpha=0.1, reg_lambda=1.0, early_stopping=50
  LightGBM:  n_estimators=500, max_depth=6, learning_rate=0.01,
             subsample=0.8, colsample_bytree=0.8, min_child_weight=5,
             gamma=0.1, reg_alpha=0.1, reg_lambda=1.0, early_stopping=50
  RandomForest: n_estimators=300, max_depth=10, min_samples_split=10,
             min_samples_leaf=5
  LogisticRegression: max_iter=1000, class_weight=None (features scaled
             via a StandardScaler fit on TRAIN only, applied unchanged to
             val/test -- ml/features/scaling.py)

Calibration: CalibratedClassifierCV(FrozenEstimator(model)), fit on the
VALIDATION split only. Both sigmoid (Platt) and isotonic are tried; the
one with the lower validation Brier score is used for test evaluation.
Every winning combo in this pass selected isotonic.

7. METHODOLOGY (TRAIN / VALIDATION / OOS)
============================================================

Stage 1 -- ABLATION x MODEL SCREEN: every (ablation, model) combo (5
ablations -- A/B/C/D/E, see Section 3 -- x 4 models = 20 combos; D was
skipped for all 4 models, see Section 4/9 below) trained on TRAIN,
calibrated on VALIDATION, evaluated ONCE on the held-out TEST split via
the real Backtester (fees, slippage, spread, funding -- BacktestConfig
defaults). Screening bar: profit factor > 1.0 AND >= 20 test trades (a
combo like C_technical_structure_regime/lightgbm that hit PF 1.45 on only
13 trades was correctly excluded at this stage -- exactly the kind of
small-sample outlier the task's own Phase 19 warns against promoting).

Stage 2 -- WALK-FORWARD + COST SENSITIVITY: ONLY the 2 combos that cleared
Stage 1 advanced to rolling walk-forward (15 folds) and a cost-sensitivity
ladder (1x/1.25x/1.5x/2x fees+slippage+funding, ml/evaluation/
cost_sensitivity.py). A combo needed >=50% of walk-forward folds
profitable AND a profit factor > 1.0 at 2x costs to be considered a real
candidate. Neither survivor cleared this bar (see Section 8-9).

No random shuffling occurred anywhere in this pipeline. Parameters were
never re-tuned after seeing OOS/test data.

16. STRATEGY CONTRIBUTION (Phase 7)
============================================================

This pass's one genuinely new empirical question: does adding the 4
PRODUCTION_ELIGIBLE strategies' own signals as ML features add real
information beyond the existing technical/structure/regime features?

Answer: NO, not on this evidence. Ablation E (C + strategy_signals)
underperformed ablation C on the Stage 1 screen for every model except
logistic regression, and even that one exception failed Stage 2 decisively
(27% of walk-forward folds profitable, net-negative under realistic cost
stress). Adding the strategy-signal features did not produce a model that
beats -- or even matches -- the technical-only/structural baselines,
despite those 4 strategies themselves carrying real, independently
validated (if modest) edges as RULE-BASED systems. This is not a
contradiction: a strategy's own edge does not automatically transfer into
being a USEFUL FEATURE for a differently-trained classifier predicting a
differently-defined target (triple-barrier LONG/SHORT/NO_TRADE, not the
strategy's own entry condition). The four strategies remain valuable as
independent, already-validated PRODUCTION_ELIGIBLE decision sources in
their own right (see services/signal_engine/multi_strategy.py) -- this
finding is specifically about their value as ML MODEL INPUTS, which this
pass found to be none.

17. MODEL LIMITATIONS
============================================================

- All AUC-ROC scores across every combo/ablation clustered at 0.49-0.52 --
  statistically indistinguishable from a coin flip on this dataset size.
- The one Stage 1 "success" with the highest screen PF (C_technical_
  structure_regime/lightgbm, PF 1.45) ran on only 13 test trades --
  correctly excluded by the pre-declared >=20-trade floor, but illustrates
  how easily a single split can produce a misleadingly strong-looking
  number from too few trades.
- Ablation D (derivatives) remains untestable at meaningful sample size
  until Binance (or another source) offers longer historical OI coverage.
- No liquidation-based features exist at all (zero historical rows,
  unchanged since Phase 2 -- docs/known_limitations.md) -- not attempted,
  not faked.
- This pass tested single-split + walk-forward robustness but did not run
  a trade-order bootstrap (unlike the rule-based strategy research in V2/
  V3) -- moot here since neither model cleared walk-forward/cost-stress in
  the first place; a bootstrap on an already-rejected model would not
  change the RESEARCH_ONLY conclusion.

20. FROZEN CONFIGURATION
============================================================

None -- there is no model to freeze a configuration for. The AI signal
orchestrator (services/signal_engine/ai_orchestrator.py) is built to
operate correctly in exactly this state: every AIDecision it produces has
probability_long/short/no_trade = None, expected_return = None, and
model_version = None, with `confidence` falling back to the strategy's own
real, already-validated quality tier (LOW/MEDIUM/HIGH, computed from R:R)
rather than an invented number. If a future research pass DOES produce a
model that survives walk-forward + cost-stress, its frozen configuration
should be written to BotState.deployed_model_metadata in exactly the shape
build_model_metadata() (ml/evaluation/ml_pipeline.py) already produces --
that plumbing exists and is tested, waiting for a model that actually
earns deployment.

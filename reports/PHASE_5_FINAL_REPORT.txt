2. COINDCX OFFICIAL API CAPABILITIES
------------------------------------------------------------
Researched directly from https://docs.coindcx.com/ (a single long-scroll
"Slate" documentation page; the Futures End Points section alone is
~85,000 characters of endpoint definitions and real code samples) --
never from tutorials, blog posts, or third-party GitHub repos for
capability decisions, per the brief. Full findings recorded in
docs/coindcx_api_findings.md. Summary:
- Public market data: active-instruments list, per-instrument details,
  recent trades, a real-time current/mark-price feed for ALL pairs in one
  call, REST candlesticks (CoinDCX's own docs recommend the WebSocket
  instead for anything time-sensitive), pair stats.
- Authenticated reads: futures wallet balance, wallet transaction ledger,
  list/filter open positions (by page or by pair/position-id), position-
  level realized-PnL/funding transactions (filterable by stage: default/
  funding/exit/tpsl_exit/liquidation), trade fill history (mandatory
  date-range), list orders (mandatory single-valued side -- buy/sell
  queried separately for a full list).
- A documented WebSocket API (Socket.IO protocol, not raw websockets)
  with both public market-data channels and an authenticated "coindcx"
  channel streaming df-position-update / df-order-update / balance-update.
- Mutating endpoints exist and are documented (create/cancel/edit order,
  update leverage, add/remove margin, exit position, create TP/SL, change
  margin type, wallet transfer) -- see section 4.

3. AUTHENTICATION
------------------------------------------------------------
Headers X-AUTH-APIKEY (raw key) + X-AUTH-SIGNATURE (hex HMAC-SHA256 of
the exact JSON-serialized request body, using the API secret as the HMAC
key). Every authenticated request embeds a `timestamp` field in the body;
every official code sample uses epoch MILLISECONDS
(int(time.time()*1000)) despite some prose elsewhere saying "seconds" --
the code samples were trusted. CoinDCX documents NO way to scope a key as
read-only vs trading-enabled -- this is recorded explicitly (section 2 of
docs/coindcx_api_findings.md) as a real constraint: the safety boundary is
entirely in AlphaOne's own code, not the exchange's key permissions.

4. READ-ONLY SECURITY ARCHITECTURE
------------------------------------------------------------
services/exchange/coindcx.py implements ExchangeMarketDataProvider and
ExchangeAccountProvider. CoinDCXReadOnlyAccountProvider exposes exactly:
get_connection_status, get_balance, get_open_positions, get_trade_history
(the shared interface) plus get_transactions/get_orders (CoinDCX-specific
reads). It has NO method resembling create_order, cancel_order, edit_order,
update_leverage, add_margin, remove_margin, exit_position, create_tpsl,
margin_type, or wallet transfer -- every one of those real, documented
CoinDCX endpoints is deliberately absent from this codebase, recorded in
docs/coindcx_api_findings.md precisely so the omission is a documented
choice, not an oversight. tests/unit/test_no_order_placement_capability.py
was extended (not replaced) to introspect CoinDCX's classes alongside
SunCrypto's, with an expanded forbidden-term blacklist (add_margin,
remove_margin, margin_type, withdraw, etc.) plus a whitelist check that
every account-provider method starts with get_ (a documented `close`
lifecycle exception aside). This test runs on every suite execution.

5. COINDCX MARKET DATA
------------------------------------------------------------
CoinDCXMarketDataProvider makes real calls (verified against a mocked
HTTP transport shaped exactly like CoinDCX's documented responses,
tests/unit/test_coindcx_provider.py) to the active-instruments,
real-time-prices, historical-trades, and REST-candlestick endpoints.
normalize_symbol()/denormalize_symbol() convert between AlphaOne's
"BTC/USDT" and CoinDCX's "B-BTC_USDT" instrument format -- a real
difference from the Binance format used throughout Phases 1-4, confirmed
from CoinDCX's own active-instruments response, not assumed.

6. COINDCX ACCOUNT DATA
------------------------------------------------------------
get_balance() computes total_equity/available_balance/used_margin from
locked_balance + cross_order_margin + cross_user_margin -- CoinDCX's own
docs literally say to ignore the wallet's `balance` field, and a test
(test_get_balance_ignores_the_balance_field_per_coindcx_docs) proves a
fabricated-looking `balance` value never leaks into AlphaOne's numbers.
get_open_positions() filters CoinDCX's per-pair rows to active_pos != 0
and computes unrealized_pnl (CoinDCX's position object has none) as
active_pos * (mark_price - avg_price) -- documented in code and
docs/coindcx_api_findings.md as AlphaOne-computed, not exchange-reported.
Every method reports NOT_CONFIGURED/UNAVAILABLE/AUTH_FAILURE/
CONNECTION_LOST rather than raising or fabricating data when credentials
are absent or a call fails (tests/unit/test_coindcx_provider.py, 14 tests).

7. POSITION MONITORING
------------------------------------------------------------
services/position_monitor/monitor.py (Phase 4I) extended, not rewritten:
ExitAlert now carries symbol/entry_price/computed-pnl (via the same
services/trade_journal/pnl.py formula used everywhere else) so the
Telegram EXIT ALERT template can show real numbers. Checks are read-only
and recommend only -- verified explicitly

Trade.status. Dedup via NotificationLog prevents the same breach being
re-alerted on every check.

8. TRADE SYNCHRONIZATION
------------------------------------------------------------
services/exchange/coindcx_sync.py: sync_positions() diffs live CoinDCX
positions against known open Trade rows (source=COINDCX_SYNC). New
positions are matched to signals via the Phase 4 matcher --
AUTO_MATCHED/AMBIGUOUS/UNMATCHED, never guessed. Positions that
disappear are closed using the REAL closing fill(s) from
get_trade_history (volume-weighted average price across however many
fills happened), via the same record_exit() function Phase 4 built for
manual exits -- reused, not duplicated. If no real closing fill can be
found, the trade is left OPEN and a FAILED SyncEvent is logged instead of
guessing a close (test_disappeared_position_with_no_closing_fill_stays_open_and_flags_event).
sync_trade_fills() idempotently ingests raw fills as TradeExecution audit
rows, keyed by a deterministic id derived from
order_id+timestamp+price+quantity+side (CoinDCX documents no single
unique fill id) -- proven idempotent
(test_sync_trade_fills_is_idempotent: identical fills synced twice
produce exactly one row).

9. ACCOUNT SYNCHRONIZATION
------------------------------------------------------------
sync_balance() pulls the wallet, records an AccountSnapshot
(equity/available_balance/used_margin, source=LIVE), and updates
Account.connection_status/last_synced_at. NOT_CONFIGURED and connection
failures are both recorded honestly (a FAILED SyncEvent, connection_status
= DISCONNECTED) -- never silently promoted to LIVE
(test_sync_balance_not_configured_never_claims_live,
test_sync_balance_failure_marks_disconnected_and_logs_event). A real bug
was found and fixed via manual browser testing: the dashboard trusted a
pre-Phase-5 account row's stale stored connection_status directly,
showing "Disconnected" instead of "Not Configured" -- fixed by checking
whether credentials are actually configured right now rather than
trusting a possibly-outdated stored value (see section 19).

10. P&L / RECONCILIATION
------------------------------------------------------------
Realized P&L on a CoinDCX-synced close comes from the real closing
fill(s), computed by the same fee-inclusive formula
(services/trade_journal/pnl.py) used for every manual trade -- no
double-counted fees. Unrealized P&L is computed (see section 6), refreshed
on every position sync, and read by the dashboard from the DB (not a live
API call on every page load, to avoid hammering CoinDCX). The existing
Phase 4 reconciliation endpoint (GET /accounts/reconcile -- theoretical
equity from deposits/withdrawals/trade PnL vs. the latest reported
AccountSnapshot) is unchanged and was exercised in the final acceptance
test; it reports NO_SNAPSHOT/OK/MISMATCH and never silently adjusts a
number on mismatch.

14. BACKGROUND SCHEDULER
------------------------------------------------------------
services/scheduler/: a CircuitBreaker (CLOSED/OPEN/HALF_OPEN, exponential
backoff, clock-injectable like the Phase 2.6 RiskEngine's `now` parameter
-- 6 tests) guards each of 4 independent jobs (account sync every 30s,
exit-alert checks every 30s, signal generation every 15 min, signal-
outcome evaluation every 15 min -- frequencies documented in
services/scheduler/jobs.py's own docstring since CoinDCX publishes no
futures-specific rate-limit table). SchedulerRunner wires these into
FastAPI's lifespan, started ONLY when SCHEDULER_ENABLED=true (default
false, so the test suite and local dev never trigger it) -- explicitly
NOT designed to run inside a serverless function. 7 tests cover each
job's circuit-breaker gating and the start/stop lifecycle; the scheduler
was never run continuously against a live account this session (see
section 19).

19. KNOWN LIMITATIONS
------------------------------------------------------------
Full detail in docs/known_limitations.md (Phase 5 section). Headlines: no
real CoinDCX credentials were available this session -- every provider/
sync/WebSocket path is verified against mocks shaped exactly like
CoinDCX's documented schemas, but a real account's actual responses
should be spot-checked before going live (see section 21). CoinDCX
documents no read-only key scoping, so a leaked key is as dangerous as
any other. The WebSocket client's connect()/reconnect path was never
exercised against a real server (message parsing and freshness logic
are fully unit-tested; python-socketio's built-in reconnection is
configured, not reimplemented). The scheduler has never run continuously
against a live account. Position "opened_at" is approximated as sync
time, not the exchange's real fill time (CoinDCX's position object
doesn't expose one). Closing a disappeared position uses a
volume-weighted-average of real fills rather than modeling each partial
fill individually. sync_trade_fills attaches raw fills to the
most-recently-opened Trade per symbol (adequate for this platform's
single-position-per-symbol model, would misattribute under concurrent
positions on the same symbol). Two real bugs were found ONLY by manual
browser verification and fixed same-session: the dashboard trusted a
stale stored connection_status instead of checking real credential state
(section 9), and trades.py/journal.py's trade serialization omitted
match_status and every live-sync field entirely, so the new Match column
silently showed "--" for every trade -- both fixed with regression tests.

21. MANUAL REAL-ACCOUNT SETUP INSTRUCTIONS

When real CoinDCX read-only credentials are available:

   SCHEDULER_ENABLED=true and restart the backend to begin continuous
   monitoring.
5. Set TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID/TELEGRAM_ENABLED=true when
   ready for real alerts -- independent of the CoinDCX credentials above.

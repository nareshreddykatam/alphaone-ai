1. RISK ENGINE CHANGES
------------------------------------------------------------
Root cause of the Phase 2.5 bug: record_trade_result()'s max-daily-loss
branch AND max-drawdown branch both set the SAME `state.kill_switch` flag,
and nothing ever cleared it. A single bad day therefore permanently ended
a multi-year backtest.

Fix: the three mechanisms are now fully independent (services/risk_engine/
engine.py):
  - Daily loss limit: enforced purely via `daily_pnl_pct`, which
    `reset_daily()` already correctly zeroes at the next UTC day. No
    longer touches kill_switch at all.
  - Consecutive-loss cooldown: unchanged trigger logic, but now uses an
    explicit precomputed `RiskState.cooldown_until` timestamp (set once
    per streak) instead of recomputing elapsed time live. Exact boundary:
    now < cooldown_until -> blocked, now >= cooldown_until -> allowed.
  - Max-drawdown hard kill: the ONLY thing that sets `kill_switch`.
    Survives daily resets and cooldown expiry indefinitely. Cleared only
    by the new explicit `reset_hard_kill()` (deactivate_kill_switch() is
    now a backward-compatible alias for it).

New: `RiskStatus` enum (ACTIVE / DAILY_LIMIT / COOLDOWN / HARD_KILL) via
`get_risk_status(now)` for observable, named state.

SECOND BUG found while gathering this phase's own statistics (also fixed):
Backtester.run() was passing each trade's return-on-ITS-OWN-NOTIONAL into
the risk engine, which treats that number as return-on-ACCOUNT-EQUITY.
Only equal for a 100%-of-equity trade (buy-and-hold). For normal
risk-sized trades this wildly overstated the risk engine's internal
drawdown relative to the real dollar equity curve, and skewed every
subsequent position size (sizing reads state.current_equity). Fixed:
Backtester now converts to `trade.pnl / equity_before_trade * 100` before
handing it to the risk engine. Also fixed a related gap where the
end-of-data forced position close never updated risk-engine state (zero
effect on any trading decision, but fixed for consistency).

All changes are fully backward compatible -- every pre-existing test
passed unmodified.

2. DAILY LOSS RESET
------------------------------------------------------------
Automatic at the next UTC calendar day. Verified: blocks same-day trades
immediately after breach, remains blocked through the rest of that day,
resumes the instant the UTC date changes -- and does NOT set the hard
kill (the actual Phase 2.5 bug). See
tests/unit/test_risk_engine_reset_semantics.py (daily-reset group).

3. CONSECUTIVE LOSS COOLDOWN
------------------------------------------------------------
Configurable via existing RiskConfig fields (cooldown_consecutive_losses,
cooldown_minutes) -- confirmed NOT hardcoded. Breakeven trades reset the
streak under a new explicit, configurable policy
(RiskConfig.breakeven_resets_consecutive_losses, default True). Exact
boundary tested to the second. A hard kill correctly survives a cooldown
expiring in the background.

4. HARD KILL SWITCH
------------------------------------------------------------
Max-drawdown breach only. Survives UTC day changes and cooldown expiry
indefinitely -- confirmed with a scenario that advances 30 simulated days
and a cooldown many times shorter than that gap, with the hard kill still
blocking at the end. Cleared only by explicit `reset_hard_kill()`.

5. SIMULATED CLOCK
------------------------------------------------------------
Every risk decision takes `now` as a parameter; the engine itself never
reads the system clock to make a decision. Verified with a scenario dated
2023 that produces identical results regardless of the real machine date
(tests/unit/test_risk_engine_reset_semantics.py::
test_risk_decisions_use_only_the_provided_simulated_timestamp). Backtester
passes the simulated candle timestamp at every decision point; paper/live
callers rely on the `now=None -> datetime.utcnow()` default, unchanged.

6. NEW TESTS
------------------------------------------------------------
- tests/unit/test_risk_engine_reset_semantics.py (21 tests): daily reset,
  cooldown start/expiry/boundary, breakeven policy, hard-kill arm/survive/
  manual-reset, simulated-clock isolation.
- tests/unit/test_risk_engine_equity_tracking.py (2 tests): risk-engine
  equity matches real dollar equity for risk-sized trades; tracks the
  backtester's own equity curve exactly.
- tests/integration/test_risk_engine_backtest_regression.py (7 tests): the

  after the kill despite 15 more days of "sure win" signals in the
  dataset, trades spread across >=3 distinct days before the kill. This is
  the scale at which the original bug was only ever visible.

11. KNOWN ISSUES
------------------------------------------------------------
- All four baselines still hit either a genuine drawdown-based hard kill
  (1h, ~10 months in) or trade profitably-adjacent-to-flat the whole
  window (4h) -- none demonstrate a strong, unambiguous edge. This is a
  reporting finding, not a code defect.
- Take-profit still lacks the gap-aware fill treatment stop-loss got in
  Phase 2.5 (docs/known_limitations.md).
- OI capped at ~30 days, no historical liquidations -- exchange
  limitations, unchanged.
- No TP2/TP3/partial exits.
- Slippage is applied but not broken out as its own line in
  BacktestResult/reports -- it's embedded in fill prices.

12. RECOMMENDATION FOR PHASE 3
------------------------------------------------------------
The risk engine is now trustworthy for continuous multi-year backtests:
daily limits and cooldowns correctly self-heal, and the hard kill is
correctly permanent-until-manual-reset rather than an accidental one. The
1h results show all three baselines eventually hit a REAL ~10% drawdown
after roughly 6-14 months and several dozen cooldown cycles -- an honest
signal that these unoptimized rules don't have enough edge to survive
sustained risk-managed trading at that configuration, not evidence of a
lingering infrastructure bug. The 4h results (all three baselines trading
the full 3 years, Donchian+ADX net +14.77% with PF 1.19 and Sharpe 0.80)
are the most encouraging data point produced so far in this project, but
one 3-year, non-independent sample and a still-modest walk-forward
profitable-fold rate (18/24) do not constitute a verified edge -- it
warrants a dedicated, skeptical follow-up (out-of-sample period held
back, transaction-cost sensitivity check, and a significance test) before
being treated as a real finding. The data/feature/backtest/risk
foundation is ready for Phase 3 ML work.
